  <name>Task 1: Create Supabase session service</name>
  <files>
    src/lib/supabase/sessionService.ts
  </files>
  <action>
    Create `src/lib/supabase/sessionService.ts` that provides all session data operations against Supabase:

    **Functions to implement:**

    1. `createTrainingSession(supabase, params)`:
       - Insert into training_sessions table
       - Params: user_id (nullable for guests), session_id, seed, mode, filters, decisions_per_session, target_stack_bb
       - Returns the created session row
       - For guest users (no user_id): still create the row but with null user_id
         * Note: RLS allows this because guest sessions won't match any user's uid -- handle this by using the anon key's permissions OR skip DB write for guests and fall back to in-memory

    2. `getTrainingSession(supabase, sessionId, seed)`:
       - Select from training_sessions WHERE session_id = x AND seed = y
       - Returns session with entries if requested

    3. `updateTrainingSession(supabase, id, updates)`:
       - Update training_sessions SET decision_index, current_spot, is_complete, etc.
       - Only update provided fields

    4. `addSessionEntry(supabase, params)`:
       - Insert into session_entries
       - Params: session_id (UUID), index, spot_id, spot (JSONB), action_id, result (JSONB)
       - Returns created entry

    5. `getSessionEntries(supabase, sessionId)`:
       - Select from session_entries WHERE session_id = x ORDER BY index ASC
       - Returns all entries for a session

    6. `getSessionWithEntries(supabase, sessionId)`:
       - Join training_sessions with session_entries
       - Returns full session data for review/replay

    7. `deleteTrainingSession(supabase, id)`:
       - Delete from training_sessions (cascades to entries)

    8. `flagEntry(supabase, entryId, isFlagged)`:
       - Update session_entries SET is_flagged = x WHERE id = entryId

    **Guest handling strategy:**
    For guests (no Supabase user), the session service should detect this and fall back to the existing in-memory sessionStore pattern. The decision of guest vs authenticated happens at the API route level:
    - If user exists: use Supabase session service
    - If no user: use existing sessionStore (in-memory) + localStorage on client

    Import types from `@/lib/supabase/types` for type safety.
    Each function takes a Supabase client as first param (created per-request in route handlers).
  </action>

    - All functions use typed Supabase client with proper table names
    - No direct Prisma imports in this file
  </verify>

  <action>
    Update all 4 session API routes to use the Supabase session service instead of the old sessionHandlers:

    1. `src/app/api/session/start/route.ts` (POST):
       - Create server Supabase client
       - Get user via `supabase.auth.getUser()` (nullable for guests)
       - If authenticated: use sessionService.createTrainingSession() to persist
       - If guest: use existing in-memory sessionHandlers.handleStart() (preserve guest flow)
       - Still call the engine/runtime layers for session creation logic (deterministic seeding, spot selection)
       - The business logic (spot loading, filtering, session creation) stays in sessionHandlers -- only the PERSISTENCE changes
       - Return same response shape as before (session snapshot + first spot)

    2. `src/app/api/session/submit/route.ts` (POST):
       - Create server Supabase client, get user
       - Call existing grading logic (engine layer -- unchanged)
       - If authenticated: save entry via sessionService.addSessionEntry()
       - If guest: use in-memory store (existing pattern)
       - Return same DecisionGrade response

    3. `src/app/api/session/next/route.ts` (POST):
       - Create server Supabase client, get user
       - If authenticated: update session via sessionService.updateTrainingSession()
       - If guest: use in-memory store
       - Return next spot (same logic as before)

    4. `src/app/api/session/[id]/route.ts` (GET + DELETE):
       - GET: Create server client, get user
         * If authenticated: fetch via sessionService.getSessionWithEntries()
         * Return session data with entries
       - DELETE: Delete session via sessionService.deleteTrainingSession()

    **Critical preservation rules:**
    - Do NOT change the engine layer (src/lib/engine/) -- it stays untouched
    - Do NOT change the runtime layer (v2SessionRegistry) -- it still handles in-memory session state during active training
    - Do NOT change the grading pipeline
    - Do NOT change response shapes -- frontend must not break
    - The sessionHandlers business logic (spot loading, filtering, grading) is REUSED -- only persistence changes

    **Dual-path pattern:**
    ```typescript
    const supabase = await createClient()
    const { data: { user } } = await supabase.auth.getUser()

    // Business logic (unchanged)
    const result = await sessionHandlers.handleStart(params)

    // Persistence (new)
    if (user) {
      await sessionService.createTrainingSession(supabase, { ...result, userId: user.id })
    }

    return NextResponse.json(result.body)
    ```
