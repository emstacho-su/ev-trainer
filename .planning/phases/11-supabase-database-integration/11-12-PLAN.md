  <name>Task 1: Fix session summary page to handle Supabase-backed sessions</name>
  <files>src/app/summary/[id]/page.tsx, src/app/api/session/[id]/route.ts</files>
  <action>
The summary page at `/summary/[id]?seed=...` calls `getSession(sessionId, seed)` which hits `GET /api/session/[id]?seed=...`. The API route first tries the in-memory session store, then falls back to Supabase. The "Request failed" error means the API is returning a non-200 response.

Root causes to fix:

1. **In-memory handler returns 404 when session was just fire-and-forget persisted to Supabase:**
   The `handleGetSession` calls `getSessionRecord` (in-memory store) and `getSession` (v2SessionRegistry). If the in-memory session exists but the registry check at line 597 fails (returns null), it returns 404. This can happen if the server restarted or if HMR cleared the registry. Fix: if in-memory handler returns 404, ALWAYS try the Supabase fallback for authenticated users (the current code only does this when `user && seed && result.status === 404`, which is correct but may not trigger for guests).

2. **Guest users can't fall back to Supabase:**
   For guest sessions (user is null), the Supabase fallback is skipped entirely, meaning any server restart loses the session. This is expected behavior for guests, but the summary page should handle this gracefully instead of showing "Request failed".

3. **Error response format mismatch:**
   The `normalizeError` in `sessionClient.ts` shows "Request failed" as the default message when the response body doesn't have `{ error: { message: ... } }` structure. The API route might be returning a malformed error or an unhandled exception (500).

Fixes:

**In `src/app/api/session/[id]/route.ts`:**
- Add a try/catch wrapper around the entire GET handler to ensure any unhandled errors return a properly formatted JSON error response (not an HTML 500 page).
- Add more defensive error handling: if `handleGetSession` throws (not returns an error result), catch it and log it, then try Supabase.
- For guest users (user is null) when in-memory returns 404, return a specific error message: "Session expired. Guest sessions are not persisted across server restarts."

**In `src/app/summary/[id]/page.tsx`:**
- The summary page currently relies on `getSession(sessionId, seed)` from the API client. If this fails, it shows the raw error message. Improve the error handling:
  - If the error is 404 and the user is a guest, show a friendly message: "This session has expired. Guest sessions are temporary. Sign up to save your progress."
  - If the error is 500, show: "Something went wrong loading your session. Try refreshing the page."
  - Check if localStorage has the session data (via `readSessionRecord`). The summary page ALREADY does this (`const stored = readSessionRecord(sessionId)`). But currently it only uses localStorage for the `seed` and `aggregates` -- not for building the actual summary. If the API call fails but localStorage has data, use the localStorage data to show the summary instead of an error.

Here's the key improvement for the summary page: make it resilient to API failures by using localStorage as a fallback.

Update the `bootstrap` function:
```typescript
async function bootstrap() {
  if (!sessionId) {
    setErrorMessage("Invalid session id.");
    setLoading(false);
    return;
  }

  const stored = readSessionRecord(sessionId);
  const resolvedSeed = searchParams.get("seed") ?? stored?.session.seed ?? null;
  setSeed(resolvedSeed);

  if (!resolvedSeed) {
    setErrorMessage("Missing seed for this session.");
    setLoading(false);
    return;
  }

  try {
    const response = await getSession(sessionId, resolvedSeed);
    if (!mounted) return;
    setDetail(response);
    updateFromSessionDetail(response);
    // ... existing aggregates logic ...
  } catch (error) {
    if (!mounted) return;

    // API failed -- try to build summary from localStorage instead
    if (stored && stored.session.isComplete !== false) {
      // We have local data, show a degraded but functional summary
      const computed = stored.aggregates ?? (
        stored.session.isComplete !== false
          ? { volume: 0, meanEvLoss: 0, bestActionRate: 0, durationMs: 0 }
          : null
      );
      setAggregates(computed);
      // Don't set errorMessage -- show summary from local data
    } else {
      const message = error instanceof Error ? error.message : "Failed to load summary.";
      setErrorMessage(message);
    }
  } finally {
    if (mounted) setLoading(false);
  }
}
```

Also ensure the `PersistedSessionRecord` interface's `session.isComplete` is checked correctly -- the `SessionSnapshot` type has `isComplete: boolean` but in localStorage it might not be set if the record was created before completion was recorded.

The goal: the summary page should NEVER show "Request failed" if the user just completed a session. It should always be able to show at least a basic summary from localStorage data.
